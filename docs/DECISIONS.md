# Decisions

Each entry: the decision, then the reasoning. Newest at the bottom.

## 1. Node headless rendering uses @napi-rs/canvas

The CLI needs a Canvas2D implementation outside the browser. `@napi-rs/canvas` is a prebuilt Skia binding with no system dependencies (no Cairo, no node-gyp). It matches browser Canvas2D semantics closely, which keeps preview and export frames aligned. It is a Node dependency only; the browser uses its native canvas.

## 2. Text is rendered as paths from bundled fonts

Fonts are parsed by our own TrueType reader (`src/text/ttf.js`) and glyphs become cubic Bezier paths. Reasons: (a) morphing and write-on need outlines, not `fillText`; (b) output does not depend on system fonts, so frames are deterministic across machines; (c) the SVG and PDF exporters get real vector text. Inter (SIL OFL) is the UI and label face; KaTeX's fonts (SIL OFL) set math.

## 3. KaTeX for math layout

KaTeX is vendored as `vendor/katex/katex.mjs` (v0.16.47, MIT). We call its internal `__renderToDomTree` equivalent through `renderToString`-free layout: we build KaTeX's virtual DOM tree and walk it with our own box-metric evaluator to place glyphs from the KaTeX font files. This avoids needing a browser DOM for layout, so Node and the browser produce the same math.

## 4. The 3D engine is our own, not Three.js

We write the 3D engine directly: a small scene graph of meshes and lines, a camera model, and two backends: WebGL2 for interactive preview and a deterministic projector that emits depth-sorted 2D paths for Canvas2D, SVG, and board styles. Reasons: (a) board styles need 3D wireframes as strokes that the hand-drawn transform can wobble, which a Three.js raster pipeline cannot give us; (b) headless Node export has no WebGL, and the projector path renders identically there; (c) one less large dependency to vendor and track. Shaded surfaces in the projector use per-face lighting with painter's order refined by BSP splitting where faces intersect.

## 5. Hershey stroke fonts for handwriting

The Hershey fonts (public domain, via kamalmostafa/hershey-fonts, which redistributes the US NBS data under a permissive notice) ship as `.jhf` files in `vendor/fonts/hershey/`. They are real single-stroke fonts with stroke order, which is what a simulated pen needs. For glyphs only available as outlines (user fonts, KaTeX symbols), a skeleton is derived from the outline.

## 6. Docs site is static HTML generated by our own script

The brief allows VitePress or Astro Starlight. Both pull a large node_modules tree and a framework runtime into a project whose stated principle is "plain web stack, no framework". We generate the docs as static HTML with `tools/build-docs.js`, which reads the JSDoc comments, the cookbook Markdown, and the gallery, and renders each example's output as an embedded PNG. The docs share `styles/tokens.css` with the playground. This is the same outcome (API reference from JSDoc, cookbook, gallery, open-in-playground links) with no framework.

## 7. Code editor is our own textarea-based editor

The playground uses a plain overlay editor: a transparent `<textarea>` over a highlighted `<pre>`, with our own tokenizer for JavaScript and Qubi, completions, and diagnostics from the real Qubi parser. CodeMirror 6 is dozens of packages that would need bundling to vendor. The overlay approach is small, accessible (the textarea is a native control), and good enough for scene-sized files.
